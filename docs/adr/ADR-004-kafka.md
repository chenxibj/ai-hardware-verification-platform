# ADR-004: 消息队列选择 Kafka

## 状态

已规划 (Proposed)

## 背景

AI 软硬件验证平台在以下场景需要异步消息处理能力：

- **评测任务分发：** 将评测任务分发到不同的 Agent 节点（GPU 服务器）执行
- **结果上报：** Agent 完成评测后异步上报结果和日志
- **事件驱动：** 任务状态变更通知、告警触发、审计日志记录
- **流量削峰：** 大批量评测计划提交时保护后端服务
- **数据管道：** 评测指标数据从采集到存储的可靠传输

当前阶段（MVP）使用 Redis 作为简易任务队列（List + BLPOP 模式），但随着平台规模增长，需要更专业的消息中间件。

## 决策

规划引入 **Apache Kafka** 作为核心消息中间件，当前阶段继续使用 Redis 队列满足基础需求。

## 理由

### 1. 高吞吐与持久化

- Kafka 的顺序写磁盘设计提供极高的写入吞吐（单 Partition 百万消息/秒）
- 消息持久化且可重放，评测结果不会丢失
- 适合大批量评测任务的并行分发场景

### 2. 评测数据管道天然适配

- 评测指标数据（性能数据点、日志流）天然是流式数据
- Kafka 的 Topic-Partition 模型匹配多设备并行评测场景（按设备 ID 分区）
- Consumer Group 实现多个下游消费者（存储、分析、告警）独立消费

### 3. 消息回溯与审计

- Kafka 消息保留策略允许任意时间点重放（评测结果需要可追溯）
- 评测审计要求所有操作可追溯，Kafka 天然满足
- 故障恢复时可从 Offset 断点续传

### 4. 生态集成

- Spring for Apache Kafka 提供声明式消费者/生产者
- 与 TimescaleDB 配合：Kafka → Kafka Connect → PostgreSQL/TimescaleDB
- 未来可接入 Flink/Spark 进行实时分析

### 5. 水平扩展

- Partition 级别的并行消费，扩容时增加消费者即可
- 多 Broker 集群提供高可用
- 适合平台从单节点到多节点的演进路径

## 后果

### 正面

- 消息不丢失：持久化 + 副本机制保证评测数据可靠性
- 解耦彻底：生产者/消费者完全解耦，各模块独立演进
- 扩展性好：天然支持多消费者、多下游场景
- 监控成熟：Kafka Manager / Burrow / JMX 提供完善监控

### 负面

- 运维复杂度高：需要 ZooKeeper（KRaft 模式可免）、Broker 集群管理
- 资源开销大：最低 3 Broker 部署，内存/磁盘要求高
- 延迟不是最优：默认批量模式下，端到端延迟高于 RabbitMQ
- 学习曲线：Partition、Offset、Consumer Group 等概念需要学习

## 替代方案

### RabbitMQ

- **优势：** 轻量、低延迟、支持多种消息模式（Direct/Topic/Fanout）、管理界面友好、AMQP 标准协议
- **放弃原因：**
  - 消息持久化后性能显著下降
  - 不支持消息回溯（ACK 后即删）
  - 在高吞吐场景（>10 万消息/秒）下需要复杂的集群配置
  - 不适合作为数据管道（Event Sourcing 场景）
- **适用场景：** 如果平台规模始终较小（<1000 任务/天），RabbitMQ 是更轻量的选择

### Redis Streams

- **优势：** 无需额外部署（已有 Redis）；API 简单；低延迟
- **放弃原因：**
  - 持久化依赖 Redis 自身（RDB/AOF），可靠性不如 Kafka
  - 内存存储，消息量大时成本高
  - 消费者组功能相对简陋（不支持精确一次语义）
  - 不支持跨数据中心复制
- **当前用法：** MVP 阶段使用 Redis List 作为简易队列，Streams 作为备选升级路径

### Apache Pulsar

- **优势：** 存算分离架构、原生多租户、统一消息和流处理
- **放弃原因：**
  - 国内社区和企业采用率远低于 Kafka
  - 运维工具链不如 Kafka 成熟
  - 对于当前规模属于过度设计
